Accelerator physics · Python

Drive SciBmad.jl from Python.

scibmad is a thin, ergonomic juliacall wrapper over the SciBmad.jl simulation ecosystem — beamline construction, tracking and Twiss — with the Python-specific glue that makes it feel native.

import scibmad as sb Python ≥ 3.9 Julia LTS 1.10 SciBmad 0.4

01Installation

Install from PyPI or conda:

shell
# either
pip install scibmad
# or
conda install scibmad

The first import scibmad uses juliapkg to install the long-term-support (LTS) release of Julia — the 1.10 series, not the latest Julia — together with the registered SciBmad.jl. These versions are pinned in scibmad/juliapkg.json, so updating the Python package (conda update scibmad) updates the Julia side in lockstep.

One-time cost

The first import downloads Julia and precompiles the SciBmad ecosystem. Subsequent imports attach to the cached environment and start quickly.

02Quick start

Build a FODO cell, then compute Twiss parameters:

python
import scibmad as sb

qf = sb.Quadrupole(Kn1=0.36, L=0.5)
qd = sb.Quadrupole(Kn1=-0.36, L=0.5)
d  = sb.Drift(L=1.0)

bl = sb.Beamline(
    [qf, d, qd, d],
    species_ref=sb.Species("electron"),
    E_ref=18e9,
)

tw = sb.twiss(bl)          # Twiss at every element
tw = sb.twiss(bl, at=[])   # `at` accepts a Python list

Element constructors, Beamline, Species and twiss are forwarded to SciBmad.jl. The at= argument takes a plain Python list of element indices, LineElements and/or (s0, s1) ranges.

03Deferred & interdependent parameters

Deferred expressions, time-dependent parameters and batch parameters all work from Python — including operator overloading.

The fix

Plain juliacall only wires Python's arithmetic operators to Julia values whose type subtypes Number. DefExpr, TimeDependentParam and BatchParam are not Number subtypes, so sb.DefExpr(lambda: 1) + 10 would fail. scibmad's Operand wrapper forwards each Python operator onto the Julia operator these types define — so the arithmetic just works.

python
k = sb.DefExpr(lambda c: c.k1)     # closes over a Context field
qf = sb.Quadrupole(Kn1=k, L=0.5)
qd = sb.Quadrupole(Kn1=-k, L=0.5)  # unary minus works

sb.DefExpr(lambda: 1) + 10                 # -> DefExpr
sb.DefExpr(lambda: 1) + sb.DefExpr(lambda: 2)
10 * sb.DefExpr(lambda: 2)                  # reflected operators too

t = sb.Time()                              # identity time parameter
ramp = 1e6 * sb.sin(2 * 3.14159 * t)       # arithmetic + math fns

b = sb.BatchParam([0.1, 0.2, 0.3])         # per-particle values

A deferred value is evaluated by calling it:

python
e = sb.DefExpr(lambda: 1) + 2
e()          # -> 3.0
Known limitation — upstream, fix pending

For a DefExpr built from a Context-accepting lambda, the operators above do not forward an explicitly supplied Context: (-k)(ctx) and (k + 1)(ctx) evaluate k against the null context rather than ctx, so they either raise “Variable … is not defined in the local Context” or, where the name resolves via GLOBAL_CONTEXTS, quietly return the wrong value. The same applies to a Beamline's stored context reaching an operator-built parameter. Zero-argument DefExprs (sb.DefExpr(lambda: a)) are unaffected, as are TimeDependentParam and BatchParam. Fixed by Beamlines.jl#161; this note comes out once that is merged and released.

04Naming elements (@elements equivalent)

Julia's @elements macro sets each element's name to its variable name. The Python equivalent is sb.elements(...), which names each element after its key and returns a namespace:

python
E = sb.elements(
    qf=sb.Quadrupole(Kn1=0.36, L=0.5),
    d=sb.Drift(L=1.0),
    qd=sb.Quadrupole(Kn1=-0.36, L=0.5),
)
E.qf.name            # -> "qf"
bl = sb.Beamline([E.qf, E.d, E.qd, E.d], species_ref=sb.Species("electron"),
                 E_ref=18e9)

For a single element, sb.name(ele, "qf") sets and returns it.

05API reference

The wrapped surface — the pieces that need Python-specific handling. Everything else is surfaced automatically (see Full SciBmad surface).

06Full SciBmad surface

Any exported name of the SciBmad Julia module is available as scibmad.<name> even when it is not wrapped explicitly — element types (Sextupole, SBend, Solenoid, RFCavity, Marker, Multipole…), functions (track, find_closed_orbit, dynamic_aperture…) and constants. Names are looked up lazily and wrapped so operands are unwrapped on the way in and re-wrapped on the way out. Names that are ambiguous at the reexport level (e.g. Context) resolve to the accelerator-facing subpackage.

python
sb.Sextupole(Kn2=0.1, L=0.2)     # not wrapped explicitly — still works
sb.find_closed_orbit(bl)
sb.Context(k1=0.36)             # resolved from Beamlines

07How it works

Bridge

Thin juliacall layer

Construction, tracking and Twiss are forwarded to SciBmad.jl. Operands are unwrapped going in, results re-wrapped coming out.

Operators

Operand wrapper

scibmad.Operand forwards Python arithmetic to the Julia operators on DefExpr / TimeDependentParam / BatchParam.

Glue

_glue.jl

Constructs deferred types from Python callables and converts the at= list — loaded at import, so the package works against the registered Julia packages today.

The path a call takes:

Python call → unwrap operands → SciBmad.jl → wrap result → Python value

08Recommended upstream Julia work

Per SciBmad.jl#76, the glue should eventually move into PythonCall package extensions in the relevant SciBmad subpackages (so no package depends on PythonCall directly), at which point the corresponding glue here can be dropped. Each piece is up as a draft PR; none is merged or released yet, so all of the glue is still required.

  • Generalize twiss(…; at::Union{Colon, Vector}) to accept AbstractVector, so a PyArray/PyList works without conversion — SciBmad.jl#81. Retires to_any_vector in the at= path.
  • DefExpr(::Py) construction from Python callables in BeamlinesPythonCallExt — Beamlines.jl#158. Retires defexpr_from_py0 / defexpr_from_py1.
  • A new BeamTrackingPythonCallExt for TimeDependentParam(::Py) and BatchParam(::Py) — BeamTracking.jl#315. Retires tdparam_from_py, batchparam_from_py, batchparam_scalar.

Beamline's own list handling already landed upstream — as of Beamlines 0.9.4 its constructor does convert(Vector{LineElement}, vec(line)), so the to_any_vector call in sb.Beamline is belt-and-braces rather than required.

Not upstream work

The operator-overloading wrappers in _wrappers.py compensate for a juliacall limitation — arithmetic dunders are only wired up for Number subtypes — not for anything missing in SciBmad, so they stay regardless.

Verified against: Julia 1.10.11 (LTS), SciBmad 0.4.2, Beamlines 0.9.4, BeamTracking 0.7.1, AtomicAndPhysicalConstants 0.10.0, PythonCall 0.9.35 — full suite passing.

09Development & testing

shell
pip install -e ".[test]"

The test suite starts a real Julia session via juliacall and exercises the SciBmad functionality end-to-end — element construction, naming, Beamline, twiss (default and at=[]), the operator-overloading fix, and time-dependent parameter arithmetic. First run is slow (Julia precompilation).
